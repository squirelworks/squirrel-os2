# 2.3.1 — Ring-3 programs under permanent long-mode stay

**Date:** 2026-11-16  
**Mark:** M2 in `TO_3.0.0.md` (ladder name `2.3.2`; this patch is the next free after `v2.3.0` because W.6 / `2.3.1` had not landed yet).  
**Lane:** `-b55f` · issue [#211](https://github.com/squirelworks/squirrel-os2/issues/211)

## Summary

32-bit ring-3 programs run while the kernel stays in IA-32e (`LM_BOOT64` / `os-lm64.img`). `run hello` and `run ring3` pass under `qemu-system-x86_64` on the boot64 image. This does **not** tick the full `2.9-lm-kernel` box.

## Changes

- `vm_load` / loader / `vm_reload_kernel` load the 4-level PML4 while `lm_perm` is set (a PAE PDPT is not a valid long-mode CR3).
- Long-mode PDPTE / PML4[0] get `PG_U` so ring-3 walks succeed; new PAE PDPTEs are mirrored into the LM wrapper (`as_pte` / `as_lm_sync`).
- 64-bit IDT exception trampolines forward to `exc_report` (stack grow resumes with `iretq`; GPFs kill the faulting process).
- `smp_on_ap` treats `SEL_TSS64` as the BSP under stay.
- Nest frames on a dying process’s kernel stack are freed from `proc_exit`.

## Checks

- `lm64-hello` — `Hello from a loaded program!` on `os-lm64.img`
- `lm64-ring3` — `ring3: PASS` on `os-lm64.img`
- Existing `lm-boot64*` / `ring3` on the 32-bit flavour unchanged

## Limits

- Linux/BSD `int 0x80` under stay still returns `-ENOSYS` (#221 / `2.9-syscall64`).
- Full regress as everyday `qemu-system-x86_64` is still the `2.9-lm-kernel` tick.
