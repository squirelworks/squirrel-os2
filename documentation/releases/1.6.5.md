# 1.6.5 — Pixel drawing in draw

- Date: 2026-10-31
- TODO.md task: **1.6-draw-pixels**.
- Changes:
  - **`g` in `draw` opens a pixel canvas**: 80 × 50 pixels, shown three times larger in graphics mode (`kernel/drawpx.asm`, `apps/draw.md`). Arrows move, Space plots, `p` puts the pen down so moving draws (a stroke), `x` or Backspace erases, `c` changes the ink (black, red, green, blue, yellow, magenta), F2 saves and Esc goes back to the text canvas.
  - **The image is a file**: `<drawing>.px` (`drawing.px` for an unnamed drawing), a 6-byte header (`SQPX`, width, height) and one colour byte per pixel, 4006 bytes. It is loaded when the pixel canvas opens.
  - **On the desktop** `draw` runs in a window. There `g` draws the pixel canvas over the desktop (already in graphics mode), and Esc puts the desktop and the window back.
  - **`drawpx`** self-check: draws a stroke the way the keys do, reads a pixel of it back off the screen, saves, clears, loads and reads it back again. It prints `drawpx: PASS`. It needs the data disk.
  - `draw`'s key help names `g pixels` (and says `p pen` for `p pen up/down`, to make room).
  - Banner `1.6.5`.
  - Regression checks: `drawpx`, `drawpx-text`, `drawpx-mem`, `draw-pixels` (F2 writes `dpx.px`), `desktop-draw-pixels`, `desktop-draw-pixels-back`.
- Known limitations:
  - One size of image and six inks; no lines, rectangles or fill on the pixel canvas yet.
  - A drawing name of more than 12 characters leaves no room for `.px`, and the pixel image cannot be saved.
  - Esc does not ask about unsaved pixels.
  - Tested in QEMU only.
- Status: implemented
